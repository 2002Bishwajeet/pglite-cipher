## 2. Detailed findings

### 2.1 PGlite and Postgres in WASM

**Upstream PGlite has no encryption and no plan for it.**
- [Discussion #243](https://github.com/electric-sql/pglite/discussions/243) (Aug 2024, converted from issue #238): Sam Willis says TDE "will likely need a custom build" and they are "unlikely to look into this ourselves". He suggests pgcrypto (column encryption) or "an encrypted VFS for PGlite". Verified.
- Custom filesystems: [#533](https://github.com/electric-sql/pglite/issues/533) and [#810](https://github.com/electric-sql/pglite/issues/810) (vitonsky, wrapping `@zenfs/core` in `BaseFilesystem`, hits "random errors" and `unreachable` on an empty-path lookup). Closed 2026-02-07 with "we'll revisit custom Filesystems when we'll get more time". So a `BaseFilesystem` pass-through is **not well supported upstream**, which is one more point for the spec's option B (subclass `EmscriptenBuiltinFilesystem` and wrap MEMFS). pglite-encrypted-fs did get option A to work in Node, so it is possible, but expect to debug WASM `unreachable` traps.

**Upstream bugs that sit on our sync boundary** (all verified on GitHub):
- [#1065](https://github.com/electric-sql/pglite/issues/1065): `transaction()` runs `COMMIT` while `#inTransaction` is still true and never calls `syncToFs()` afterwards, so a resolved transaction may not be persisted. A commenter reproduced lost rows with `idb://` after reload on 0.5.15. The issue is closed (2026-11-04), but fix PR [#1066](https://github.com/electric-sql/pglite/pull/1066) was closed unmerged and [#1205](https://github.com/electric-sql/pglite/pull/1205) ("sync once per query through PGliteWorker, and when a transaction ends") is still open.
- [#1191](https://github.com/electric-sql/pglite/issues/1191) (open): `syncToFs()` resolves immediately, without syncing, when another sync is already queued.
- [#1063](https://github.com/electric-sql/pglite/pull/1063) (closed): under `relaxedDurability` a failed background sync was an unhandled rejection after which nothing ever persisted again, and `close()` could close the FS mid-sync.
- Whether Journal's `pgliteWorkerHost.ts` / `TimedIdbFs` already work around these is **[unverified]**; I did not read Journal code for this report.

**pglite-encrypted-fs** (rank 1). Read in full (`src/crypto.ts`, `src/encrypted-fs.ts` 1,347 lines, tests).
- Design: `class EncryptedFS extends BaseFilesystem`, every `write()` does read-decrypt-modify-encrypt-write of each touched 8 KB page synchronously with Node `crypto` and `fs.writeSync`. On disk: `[salt 16][fileId 32]` header per file, then `[IV 12][tag 16][ct 8192]` records. Logical size is reported as `pages * 8192` and a non-aligned physical tail throws `EIO`.
- Good choices that match the spec: random per-write IV, AAD binds a random per-file ID and the page number, so renames rewrite nothing and cross-file swaps fail; **every page is padded to 8192** (this is the review's S3 fix); a `.encryption-verify` file holds an encrypted magic to report a wrong passphrase before PGlite touches anything.
- Gaps, each of which the spec already avoids:
  - **No crash atomicity.** A multi-page write or a torn page leaves an undecryptable page and the read path throws `EIO` with no recovery. The spec's single IndexedDB transaction per sync is the fix.
  - **Plaintext files:** `*.conf`, `*.pid`, `PG_VERSION`, `pg_internal.init`, `postmaster.*`, `*.lock`, `replorigin_checkpoint` are stored unencrypted. `pg_internal.init` is a relcache dump of catalog rows; the README's claim that these "contain no user data" is doubtful **[unverified for pg_internal.init content]**. The spec encrypts every file, which is better.
  - File IDs live in plaintext headers and inode metadata (sizes, names, directory tree) is the host FS's, so names and page-granular sizes leak.
  - No key rotation ("dump and re-import"), passphrase-only (no raw-key mode), Node-only.
- Tests worth porting: `test/integration/pglite-basic.test.ts` (525 lines: CRUD, reopen, large rows, indexes), `pglite-failure.test.ts` (262 lines: wrong passphrase, tampered page, truncated file, missing verify file), `pglite-pgvector.test.ts` (extension over the encrypted FS), `test/unit/crypto.test.ts` (IV uniqueness, AAD swap detection). Benchmarks in `bench/` (crypto overhead, startup, operations).

**pgdarq-afs** (rank 5): a fork that tried two other backends.
- Branch `pgdarq-afs`: a PGlite FS ("AFS") whose inodes, dentries and 8 KiB chunks are rows (`src/pgdarq-afs-schema.ts`), flushed as batches (`PgdarqAfsFlushBatch`) to a Turso database on OPFS. PGlite runs in a worker and reads synchronously through a SharedArrayBuffer/Atomics broker that, in the WIP, lives on the main thread (`docs/main-thread-minimization.md`).
- Branch `cryptograft-afs`: the same over Graft (a SQLite page-sync layer), with commit "removing sqlite3mc due to clash with graft".
- Both stop at "WIP: mostly works" in March 2026, with an empty benchmark report. Its schema (inode, dentry, chunk, batch with created/deleted/upserted sets) is a near-copy of the spec's record model, which is a sign the model is natural, and its abandonment is a sign the SQLite-as-backend route is not free.

**Postgres TDE.** The spec already covers the PG wiki, Cybertec and pg_tde. Update: [pg_tde 2.0](https://docs.percona.com/new/2025/09/01/percona-transparent-data-encryption-pg_tde-20-has-been-released/) made WAL encryption production-ready, and [2.2.0](https://docs.percona.com/pg-tde/release-notes/release-notes-v2.2.0.html) (May 2026) added AES-256 and requires Percona's patched server 17.10 / 18.4 or newer. Nothing changes the spec's rejection: it still needs a patched server and SMGR hooks that PGlite does not ship.

### 2.2 SQLite in WASM with encryption

**SQLCipher 5 (beta) is the most important finding for the format.** Verified in `src/sqlcipher.c` at tag `v5.0.0-beta.1` (around L2095-L2150) and the [beta CHANGELOG](https://github.com/sqlcipher/sqlcipher/blob/beta/CHANGELOG.md):
- AES-256-GCM replaces CBC+HMAC-SHA512 as the default. Default page size moves to 8192.
- Per page write, SQLCipher draws a 12-byte random **KDF context** and a 12-byte random IV, derives a **one-time subkey** with an SP 800-108 counter-mode KDF over AES-256-CMAC (label `0x58`, "modeled after XAES-256-GCM"), and encrypts with GCM under that subkey with AAD = page number (big-endian u32). Reserve = context 12 + IV 12 + tag 16 + 8 random = 48 bytes.
- The source comment quotes the NIST SP 800-38D 2^-32 bound and says plain 96-bit random IVs "only satisfies the NIST 2^-32 threshold up to 2^32 encryptions per key", which "high-write-volume use cases" could exhaust; with the subkey the limit becomes 2^80 page writes, "so large that effectively a master key will never require rotation".
- 5.0.0-beta moved to VFS shims, then beta.1 went **back to the codec architecture**, adds `PRAGMA cipher_selftest`, plaintext-to-encrypted `rekey`, ships a reference database `sqlcipher-5.0-testkey.db`, and locks down journal spill "to prevent plaintext writes".
- The construction is specified in [C2SP XAES-256-GCM](https://github.com/C2SP/C2SP/blob/main/XAES-256-GCM.md) (Filippo Valsorda): 192-bit nonce, random nonces safe for 2^80 messages at 2^-32 collision risk, built only from AES-256 and AES-256-GCM. Bitwarden's SDK also implements it ([docs](https://sdk-api-docs.bitwarden.com/bitwarden_crypto/hazmat/symmetric_encryption/xaes_256_gcm/index.html)) **[not read beyond the index page]**.

**SQLite3 Multiple Ciphers (sqlite3mc).** [Repo](https://github.com/utelle/SQLite3MultipleCiphers), MIT, 2.6.1 on 2026-10-12. Every release ships `sqlite3mc-<v>-sqlite-<v>-wasm.zip` and a `-wasm-simd128.zip` (verified in the release assets), first in 1.8.1. Ciphers: wxSQLite3 AES-128/256, sqleet ChaCha20-Poly1305 (default in PowerSync), SQLCipher (compatible formats incl. v4), System.Data.SQLite RC4, Ascon-128, AEGIS ([overview](https://utelle.github.io/SQLite3MultipleCiphers/docs/ciphers/cipher_overview/)). ChaCha20: 16 B nonce, 16 B Poly1305 tag, 32 B reserve, "one-time keys per database page are derived from the encryption key, the page number, and a 16 bytes nonce", PBKDF2-SHA256 64007 iterations ([doc](https://utelle.github.io/SQLite3MultipleCiphers/docs/ciphers/cipher_chacha20/)).
- **Caution, from the 2.6.1 release notes:** 2.6.0 and 2.6.1 have a ChaCha20 counter-overflow bug where the accelerated and scalar code paths produce different keystreams after a 32-bit counter wrap, and because the tag is over ciphertext the page **decrypts silently to wrong data with no authentication error**. Probability about 1.5e-8 per 4 KiB page write. This is a live example of a cross-implementation bug that our design must test for (section 5, test approaches).
- Evolu found and reported a raw-key parsing bug in 2.2.4 ([issue #218](https://github.com/utelle/SQLite3MultipleCiphers/issues/218)): `x'<hex>'` was treated as a passphrase.

**sqlite3mc over wa-sqlite in production.**
- PowerSync web, `packages/web/src/db/adapters/wa-sqlite/RawSqliteConnection.ts` (verified): after loading the module it calls `module.ccall('sqlite3mc_vfs_create', 'int', ['string','int'], [filename, 1])` to wrap the JS VFS, then runs `PRAGMA key = '<escaped>'`. Works with `IDBBatchAtomicVFS` and OPFS VFSes. The key is a passphrase string from the app; there is no key management.
- Notesnook web, `apps/web/src/common/sqlite/sqlite.worker.ts` (verified): vendored wa-sqlite, registers `IDBBatchAtomicVFS` or `AccessHandlePoolVFS` and opens with VFS name `multipleciphers-${vfs.name}`, then waits for `PRAGMA key` before any other query. Its key store (`apps/web/src/interfaces/key-store.ts`) has an unusually honest comment: non-extractable CryptoKeys in IndexedDB are "not super secure", anyone with script access can use, delete or modify them, and the store is only really protected when the user turns on app lock with a password. Notesnook desktop uses `better-sqlite3-multiple-ciphers` 11.5.0. Notesnook's v3 announcement: [blog](https://blog.notesnook.com/introducing-notesnook-v3).

**Evolu** (rank 2), from the package [README](https://github.com/evoluhq/evolu/blob/main/packages/sqlite-wasm/README.md), [`evolu_page.h`](https://github.com/evoluhq/evolu/blob/main/packages/sqlite-core/src/evolu_page.h), [CHANGELOG](https://github.com/evoluhq/evolu/blob/main/packages/web/CHANGELOG.md) and [issue #757](https://github.com/evoluhq/evolu/issues/757), all verified:
- Moved from sqlite3mc's WASM, to a TypeScript codec on `@awasm/noble`, to its own C codec inside the WASM. Format stays SQLCipher 4 as sqlite3mc writes it, so all versions interoperate.
- Key hygiene: key staged in WASM memory for the open and zeroed; codec keys in a separate `malloc` allocation, not SQLite's heap, wiped on destroy. They note that a memory-disclosure bug in SQLite can now reach the key, whereas the TS codec exposed plaintext but not the key.
- Constant-time AES because WASM has no AES instructions and table AES leaks through caches to "another tab or app". Numbers above. Issue #757 plans to switch to SQLCipher 5's GCM format, noting CBC encryption fills only one of four bitsliced lanes.
- Testing: SQLite's and wa-sqlite's tests ported; failure-path tests (interrupted transaction, storage full, lock conflicts) in Chromium, Firefox and WebKit in CI; codec tested against sqlite3mc 2.2.4, against the previous TS codec, and against an independent implementation on `node:crypto`; reproducible WASM build pinned by hash.
- They found that SQLite's `opfs-sahpool` "never rolled back a transaction interrupted by closing a tab", and a data-loss bug with overlapping connections; both fixed upstream in SQLite 3.54.0 ([forum](https://sqlite.org/forum/forumpost/b2fbb61642)).
- Encrypted DBs keep `secure_delete` on and refuse to turn it off, "because a freed page SQLite doesn't write would fail to authenticate".
- Where the key comes from: a BIP-39 mnemonic owner secret per Evolu's docs **[unverified, docs page 404'd]**.

**SQLite Encryption Extension (SEE) in WASM** ([sqlite.org/wasm/doc/tip/see.md](https://sqlite.org/wasm/doc/tip/see.md), verified): buildable from a licensed `sqlite3-see.c`, but a licensee "may not host an SEE WASM build on a public-facing site". The page also says "there is no known way in JavaScript to reliably hide SEE encryption keys". Unusable for a distributed app (the Tauri bundle is a distribution) **[my reading of the licence; ask Hwaci if it matters]**.

**SQLCipher's own WASM.** Zetetic ships no WASM build that I found. [7mind/sqlcipher-wasm](https://github.com/7mind/sqlcipher-wasm) builds SQLCipher 4.9.0 with OpenSSL 3.3.2 for Node, browsers and Unity WebGL (licence "Other" on GitHub, MIT badge in README; last push 2026-10-19, 4 stars). It only imports and exports whole DB bytes through MEMFS, no persistent VFS. sql.js has no maintained SQLCipher port that I found.

**Turso** (rank 10), `core/storage/encryption.rs` (verified, HEAD on 2026-11-10): random nonce per page write (`OsRng`), nonce and tag in SQLite's reserved bytes, page 1's 100-byte header in plaintext but used as AAD. For every other page `encrypt_raw` passes `AD = b""`, so **a valid page copied to another page number authenticates**. The [blog](https://turso.tech/blog/introducing-fast-native-encryption-in-turso-database) (2025-10-07) gives 6 % read / 14 % write overhead with AEGIS-256 and takes a raw hex key. The browser package `@tursodatabase/database-wasm` uses OPFS; whether encryption is enabled in it is **[unverified]**.

**Others.** absurd-sql: no encryption, last push 2023-08. cr-sqlite: no encryption (CRDT layer). These are not analogues.

### 2.3 Encrypted IndexedDB and storage layers

All of these are **record- or field-level**, not block-level, and none encrypts indexes or keys. They are not alternatives for a Postgres data directory, but some inform record format and the "unencrypted index" trade-off.

- **RxDB** ([docs](https://rxdb.info/encryption.html)): storage wrapper encrypting the fields listed in the schema's `encrypted` array. Free plugin `encryption-crypto-js` (crypto-js AES, password into `AES.encrypt`, which per RxDB's own docs is weak, MD5 KDF and CBC without MAC **[unverified detail]**); premium WebCrypto plugin (AES-CTR/CBC/GCM). Encrypted fields cannot be queried or indexed. Vendor claim: WebCrypto plugin about 5x faster than crypto-js.
- **dexie-encrypted** ([repo](https://github.com/dexie/dexie-encrypted), MIT, push 2026-03-27): tweetnacl `secretbox` (XSalsa20-Poly1305, 24 B random nonce) on non-indexed fields. Its README explains why not WebCrypto: no synchronous API, which "does not play well with IndexedDB transactions", and claims tweetnacl was faster **[old claim, not re-measured]**. This is the same transaction-lifetime hazard the review's S7 raises: no `await` on crypto inside an IndexedDB transaction.
- **localForage** (Apache-2.0, last push 2024-07): no encryption; community wrappers only. **idb / idb-keyval**: none. **TinyBase** (active): no at-rest encryption found **[unverified]**. **Replicache** repo archived (2022); Zero: no at-rest encryption found **[unverified]**.
- **Evolu**: see 2.2; it is the one local-first framework that encrypts the local DB.

| **Chromium** | No storage encryption for IndexedDB beyond the OS; nothing applicable found **[unverified]** | | |

**Key storage primitives.**
- [Electron `safeStorage`](https://www.electronjs.org/docs/latest/api/safe-storage) (verified): macOS Keychain, protected from other apps "without user override"; Windows DPAPI, protected from other users **but not other apps in the same userspace**; Linux kwallet/libsecret, or `basic_text`, which uses a hardcoded password and protects nothing. The sync API is deprecated, removed in Electron 46.
- [Tauri Stronghold](https://github.com/tauri-apps/plugins-workspace/tree/v2/plugins/stronghold) (official, still maintained): password-encrypted snapshot file, so it needs a user password and does not use the OS keychain. Not a fit for "key in the keychain". Community [`tauri-plugin-keyring-store`](https://docs.rs/tauri-plugin-keyring-store) wraps the Rust `keyring` crate **[not evaluated]**; using the `keyring` crate directly from a Tauri command is the common pattern **[unverified]**.

### 2.5 Write-ups: Emscripten FS encryption, WASI, block AEAD and nonce limits

- **Emscripten:** no write-up or library for encrypting IDBFS, MEMFS or WASMFS found. IDBFS is MEMFS plus `syncfs` reconciliation, as the spec says.
- **WASI:** no encrypted filesystem proposal or library found.
- **GCM nonce limits in practice:**
  - NIST SP 800-38D §8.3: random 96-bit IVs capped at 2^32 invocations per key (the spec and review already use this).
  - SQLCipher 5 uses per-write subkeys precisely because SQLite databases "may be written very frequently" (2.2). Turso and Firefox use random nonces without subkeys (Turso's AEGIS has a 256-bit nonce, so no issue; Firefox keys live only for one session).
  - gocryptfs uses a 128-bit random GCM IV. With GCM a non-96-bit IV goes through GHASH, which is allowed but less analysed **[my note; the gocryptfs page gives no rationale]**.
  - sqlite3mc's ChaCha20 overflow bug (2.2) shows that "the tag verifies" does not prove "the plaintext is right" when two implementations disagree on the keystream.
- **Design docs** used by the spec (SQLCipher design page, PG TDE wiki, pg_tde architecture) were checked by the review and are not repeated here.

## 3. What we should reuse or copy

**Format choices**
1. **Copy SQLCipher 5's answer to the nonce budget: derive a subkey from a random context, and put the page position in the AAD.** Three ways to do it with WebCrypto:
   - **Per-record XAES:** too costly in WebCrypto. Each block would need two one-block AES encryptions (CBC with a zero IV), an `importKey` of the derived raw bytes and the GCM call, so four async calls per block. The derived key bytes would also sit in the JS heap.
   - **Per-sync subkey, recommended:** at the start of each sync, draw a random 16 B `batchCtx` and derive `K_batch = HKDF-SHA256(DEK, salt = batchCtx, info = "pglenc v1 block")` with `crypto.subtle.deriveKey`, non-extractable. Encrypt that sync's blocks under `K_batch` with random 96-bit IVs. Each record stores `batchCtx` next to its IV. One sync encrypts at most a few thousand blocks, so the per-key count stays far below 2^32 forever. At open, derive each distinct `batchCtx` once and cache it. The number of distinct contexts is bounded by the number of syncs whose blocks are still live, which is **[unmeasured; spike item]**. `deriveKey` with HKDF is in every current WebCrypto **[WebKitGTK unverified]**.
   - **Keep the spec as is:** random IVs under the DEK, the 2^30 counter and forced rotation. It is safe by the review's arithmetic, but it needs the write counter, rotation code and their tests.
   - Recommendation: per-sync subkey. It turns rotation from a safety requirement into an optional feature, and costs 16 B per record plus one HKDF per sync.
2. **AAD = record type ‖ fileId ‖ blockIdx**, as gocryptfs, SQLCipher 5 (page number), pglite-encrypted-fs and the spec do. Turso's empty AAD is the counter-example to cite in the design doc.
3. **Pad every block to the unit size**, as pglite-encrypted-fs does (review S3).
4. **Random per-file ID in the AAD, path only inside an encrypted inode.** pglite-encrypted-fs and gocryptfs both use random file IDs, which confirms the spec's rename-is-free design. pglite-encrypted-fs keeps file names in the clear; we should not.
5. **A key-check that runs before the engine touches anything**: pglite-encrypted-fs's verify record, SQLCipher's page-1 HMAC, and our header unwrap. The review's S2 point stands: the DEK unwrap tag is the key check, so no separate `keyCheck` is needed.

**Code**
- From **pglite-encrypted-fs** (MIT): port the integration test scenarios (`test/integration/pglite-basic`, `pglite-failure`, `pglite-pgvector`) and the benchmark harness shape (`bench/startup`, `bench/operations`, `bench/crypto-overhead`). Do not port `encrypted-fs.ts`; it is option A and Node-only.
- From **wa-sqlite `IDBMirrorVFS.js`** (MIT): its IndexedDB layout (`blocks` keyed `[path, offset]`, a `tx` store keyed `[path, txId]`) and the check that "our view of the database is up to date" before writing. That is the review's S6 stale-writer fencing, already worked out for multi-tab. Read about 150 lines around `jLock`/`xSync` before writing `putBatch`.
- From **pglite-opfs-repacked** (MIT): its durability contract text ("relaxed"/"strict", what termination it survives, what it does not promise) and its treatment of non-awaited syncs as a terminal error. Reuse the contract's wording style, and its extent/metadata-log layout if we build the Tauri file backend.
- From **Element**: the rule in `apps/desktop/src/ipc.ts` `createPickleKey`: never create a new key while an existing wrapped key is present but undecryptable. From **Signal** `getSQLKey()`: refuse Linux `basic_text`, record the backend and fail loudly if it changes, and migrate a legacy plaintext key. These map directly onto #1017's keychain command.

**Test approaches**
- **Cross-implementation format test** (Evolu): a second, independent decoder of format v1 written on `node:crypto` in the test suite, run against stores written by the browser code, and the reverse. It would have caught a bug like sqlite3mc's ChaCha20 overflow.
- **Frozen reference store** (SQLCipher 5 ships `sqlcipher-5.0-testkey.db`): commit a small v1 store with a known test key as a fixture, and require every future version to open it.
- **Real engines in CI** (Evolu): run the FS tests in Chromium, Firefox and WebKit, not just Node, plus an interrupted-transaction test (close the worker mid-sync, reopen, compare). Evolu's discovery of the `opfs-sahpool` rollback bug shows these find real bugs.
- **Self-test at open** (SQLCipher 5's `PRAGMA cipher_selftest`): encrypt and decrypt a known vector with the live WebCrypto before trusting the store, since webview crypto differs by platform.
- **Tamper suite** (pglite-encrypted-fs `pglite-failure.test.ts`, SQLCipher `cipher_integrity_check`): flip a byte, swap two blocks, move a block between files, truncate, delete a file. Assert the exact error type, and assert that the store is unchanged afterwards.
- **Upstream-bug regression tests**: `transaction()` followed by an immediate reload (#1065), and a second `syncToFs()` while one is queued (#1191). These belong in Journal's suite whatever the FS.

## 4. Is there something we should adopt instead of building?

Short answer: **there is no drop-in for PGlite in a webview.** Three adopt-or-build options deserve a real answer.

**A. Adopt pglite-encrypted-fs.** No. It is alpha with an unversioned format, Node-only, synchronous, and not crash-atomic. It leaves several PGDATA files in plaintext and has no rotation or raw-key mode. Making it work in a webview means rewriting its storage and its crypto, which leaves nothing of it but the tests. Reuse the tests and benchmarks (section 3), and perhaps contact the author, who has hit the same PGlite FS problems.

**B. Use SQLite3MultipleCiphers or SQLCipher in WASM as the block store under our PGlite FS** (MEMFS and dirty tracking stay ours; blocks become rows in an encrypted SQLite on `IDBBatchAtomicVFS` or OPFS, as PowerSync and Notesnook run it).
- Gains: a proven page format, `rekey`, `cipher_integrity_check`, and atomic commits.
- Costs:
  - A second ~0.9-1.1 MB WASM engine in the worker. sqlite3mc's full build is 1,068,015 B per Evolu's measurement.
  - Every 8 KB block becomes a row inside a 4-8 KB SQLite page, plus SQLite's journal, so writes are amplified about 2-3x **[estimate]**.
  - Crypto moves from WebCrypto's native AES into WASM with no AES instructions. Evolu measures 40-70 µs per 8 KiB page there, against a few µs native. 12,800 pages at open is then about 0.5-0.9 s of crypto alone **[extrapolated]**.
  - The key must still be handed to WASM inside the webview, so the review's S9 risk does not go away.
  - The one public attempt, pgdarq-afs, stalled.
- It also does not remove our hard part. The difficult code is dirty-block tracking and the open/migrate state machine (review B2 and B3), not the 150 lines of AEAD.
- Verdict: **not better than building on WebCrypto with the per-sync subkey.**

**C. Put the encrypted store in Rust: SQLCipher 5 or sqlite3mc native, keyed from the OS keychain, with JS shipping dirty blocks over IPC** (the review's S10).
- This is how the strongest prior art does it. Signal (SQLCipher in the main process, key in `safeStorage`) and Notesnook desktop (`better-sqlite3-multiple-ciphers` in the main process) both keep the key out of the renderer.
- Gains:
  - The key never enters the webview. That removes the review's S9 and #1017's main risk.
  - Native AES-NI or ARMv8 crypto, real `fsync` and atomic SQLite transactions.
  - A format other tools can open, and SQLCipher 5's subkeys solve the nonce budget for free.
- Costs:
  - The IPC path. Tauri `invoke` is not available in workers, so blocks hop worker → page → Rust. A custom URI scheme that a worker can `fetch` is **[unverified]**.
  - Binary IPC throughput is unmeasured.
  - No IndexedDB package for the parked browser case (#554), which matters little now that encryption is native-only.
  - SQLCipher 5 is beta until a 5.0 release. SQLCipher 4 (CBC + HMAC with random IVs, so no GCM nonce cap) or sqlite3mc's stable schemes work today.
- Verdict: **for a native-only paid feature this is the strongest option and the closest to what shipping apps do.** I recommend the owner decide between C and the spec's IndexedDB design *before* phase 1. The decider is a one-day spike on worker → Rust binary throughput (sync of N dirty 8 KB blocks, and open of 12,800 blocks). The JS dirty-block tracker is needed in both designs, so that work is not wasted either way.

**D. Move Journal from PGlite to SQLite** (wa-sqlite + sqlite3mc, or Evolu's stack, which solve encryption off the shelf). Not justified by encryption alone: it would replace the database engine, the extensions (`pg_trgm`), the queries and the migration path. Mention it only as the fallback if PGlite's FS layer proves unworkable in the spike.

## 5. What changes in our plan because of this

1. **Nonce handling (spec §4).** Replace "random 96-bit nonce under the DEK, counter at 2^30 forces rotation" with a **per-sync HKDF subkey** (section 3, item 1). Keep the counter only as telemetry. Cite SQLCipher 5 and XAES-256-GCM as the precedent. If option C is chosen, SQLCipher 5 does this itself.
2. **Owner decision moves forward.** The review's S10 (Rust store) becomes a decision before phase 1, not phase 3, because the two most comparable shipping apps (Signal, Notesnook desktop) do exactly that, and SQLCipher 5 now provides GCM with subkeys natively.
3. **Keychain command (#1017)** must:
   - tell "no key" apart from "key present but unreadable now", and never mint a new key in the second case (Element);
   - refuse Linux `basic_text` or other non-protecting backends, and record the backend so a change is reported rather than treated as a new install (Signal);
   - state per-platform protection honestly, e.g. Windows DPAPI does not stop same-user apps (Electron docs).
4. **PGlite durability boundary.** The FS must not assume PGlite calls `syncToFs()` after `transaction()` (#1065, fix still open in #1205) or that a queued `syncToFs()` really syncs (#1191). Journal's worker host should call and await its own sync after transactions, or the FS should treat "dirty sets non-empty at close/hide" as a forced sync. Add the regression tests. This also affects today's plaintext `IdbFs` **[whether Journal already works around it is unverified]**.
5. **Hook choice confirmed.** Upstream says custom `BaseFilesystem` implementations are unsupported (#810), and the only working one is Node-only. This reinforces option B (MEMFS wrap) in the spec.
6. **Test plan additions (spec phase 1):** an independent `node:crypto` decoder, a frozen v1 fixture store, an open-time self-test, Chromium/Firefox/WebKit runs, an interrupted-sync test, and a port of pglite-encrypted-fs's failure and pgvector scenarios.
7. **Benchmark expectations (spec phase 0).** pglite-encrypted-fs's Node numbers (+93 % bulk insert, +138 % reopen with *synchronous* per-write crypto) are an upper bound for option A, not for us. Evolu's WASM-crypto numbers bound option B in section 4. No one has published WebCrypto per-call overhead for 8 KB blocks in a worker. Our own `gcmbench.mjs` spike in this folder is the only source, so the open-time gate stays a spike item.
8. **No change** to: block-level AEAD below Postgres, padding, random file IDs in AAD, one atomic transaction per sync, two-tier KEK/DEK, the rejection of pg_tde and SEE.
